# Terraform, File by File — Explained So You Can Teach It

Before the files: what is Terraform actually doing, and why does this project use it at all?

**The plain-English idea:** instead of logging into the AWS Console and clicking "Create VPC," "Create Database," "Create Kubernetes Cluster" by hand — a process that's slow, unrepeatable, and impossible to review like code — you write text files that *describe* the AWS resources you want to exist. Terraform reads those files, compares them against what's *actually* running in your AWS account right now, and figures out the exact set of create/change/delete API calls needed to make reality match the text. Run it again with no changes to the text, and it does nothing — reality already matches. This is **Infrastructure as Code**, and the core promise is: the text file *is* the documentation, and it's always accurate, because it's not describing the infrastructure, it's the thing that *built* the infrastructure.

**Why does that matter enough to be worth the learning curve?** Three concrete reasons: (1) you can review infrastructure changes the same way you review code changes — a pull request, a diff, a second pair of eyes before anything real happens; (2) it's repeatable — the exact same environment can be torn down and rebuilt identically, which this project actually does routinely during development; (3) it's self-documenting in a way a wiki page never stays — the wiki can drift out of date, the Terraform file *cannot*, because if it didn't match reality, the next `terraform plan` would show a difference.

**One Terraform vocabulary word you need before anything else makes sense: a "module."** A module is just a reusable, self-contained folder of Terraform files with its own inputs (variables) and outputs — think of it like a function in a normal programming language. This project has 8 modules under `modules/`, each responsible for one coherent piece of infrastructure (the network, the database, the Kubernetes cluster, etc.), and one root set of `.tf` files that calls those modules and wires their outputs into each other's inputs — the same way a `main()` function calls smaller functions and passes the results between them.

## Part 0: Terraform, explained with zero jargon, for someone who's never touched a computer's insides

Forget code for a second. Imagine you want a house built. There are two totally different ways to get it done:

**Way one — you stand there and give a worker instructions out loud, one at a time:** "dig here," "now pour concrete," "now put up this wall." If you walk away, nothing happens. If you forget what you already told them yesterday, you might tell them to dig the same hole twice, or forget to tell them about the electrical wiring at all. And if your friend wants an identical house built somewhere else, they can't just "run your instructions again" — they weren't written down anywhere, they were just said, once, to one specific worker, about one specific house.

**Way two — you hand a foreman a blueprint.** The blueprint is a *document* that describes what the finished house should look like: 3 bedrooms, 2 bathrooms, a garage. The foreman's job is to look at the blueprint, look at what's actually standing on the lot right now (maybe nothing yet, maybe a half-built house from last week), and figure out exactly what work is still needed to make reality match the blueprint. Nothing more, nothing less. Show the foreman the same blueprint again next month, and if nothing's changed, he does nothing — the house already matches. Change the blueprint to add a fourth bedroom, and he only builds the new bedroom, without touching the rest of the house.

**Terraform is way two, for computers instead of houses.** "The cloud" — AWS, in this project's case — just means "computers and storage that live in Amazon's buildings, that you rent by the hour instead of buying and plugging in yourself." Instead of a person clicking buttons in a website to rent a database, rent a network, rent some servers, you write a text document (the "blueprint") describing what you want to exist, and Terraform — the foreman — reads it, checks what's already actually running in your AWS account, and makes the two match.

**Why this matters more than it sounds like it should:** the blueprint is a real, permanent document. Anyone can read it and know *exactly* what's supposed to exist, without having to go click through AWS's website checking. Two people can review a *change* to the blueprint before it happens, the same way you'd review a change to a written contract before signing it — instead of finding out after the fact that someone clicked the wrong button. And the exact same blueprint can be handed to a second foreman to build an identical second house somewhere else — this project genuinely gets torn down and rebuilt from scratch routinely during development, and that's only sane to do because the blueprint, not any one person's memory, is the source of truth.

**A few words you'll see constantly, translated once, plainly:**

- **"Resource"** — one single thing on the blueprint: one database, one network, one server. The blueprint is made of many resources.
- **"Module"** — a reusable mini-blueprint, like a standard "bathroom" template an architect reuses in every house instead of redrawing a bathroom from scratch each time. This project has 8 of these (one for the network, one for the database, one for the Kubernetes cluster, etc.) — see Part 2.
- **"Variable"** — a blank field on the blueprint, filled in per-project: what color paint, which city. Here: which AWS region, what the website's domain name is, and so on.
- **"Provider"** — a specialist contractor who only knows how to deal with one company. The `aws` provider only knows how to talk to Amazon's systems; a separate `helm` provider only knows how to install software once a computer already exists. Terraform itself doesn't know how to do any actual work — it delegates every real action to the right specialist.
- **"State file"** — the foreman's personal notebook, where he writes down everything he's actually built so far. Without it, the foreman would have no memory between visits and might build the whole house again from scratch every time. This project keeps that notebook in a shared, safe storage box (Amazon S3) so more than one foreman (person, or an automated CI robot) can use the same notebook without two of them getting confused about what's already built.
- **"Plan" vs "Apply"** — `plan` is the foreman saying out loud "here's exactly what I'm about to do, before I do any of it" — you can read that and stop him if something looks wrong. `apply` is him actually picking up the tools and doing it. Never skip straight to `apply` without reading the `plan` first — that's the single most important habit in this entire workflow, the same way you'd never sign a contract you hadn't read.

Once those six words are solid, the file-by-file walkthrough below will make sense even to someone who has never opened a terminal.

## Part 1: The root files — the "main program" that wires everything together

These live directly in the project's top folder, not inside `modules/`. Terraform doesn't actually care what you name your `.tf` files — it reads every `.tf` file in a directory as one combined program — but this project splits them by *topic*, purely for human readability. Knowing that is itself a good thing to say if someone asks "why are there 14 files instead of one big one": **file boundaries are a human convenience, not a Terraform requirement.**

### `versions.tf` — the rulebook: which Terraform, which providers, where state lives

This file does three jobs:
1. Pins the minimum Terraform version (`>= 1.10.0`) — so nobody runs this with an ancient version that doesn't understand a feature the code uses (here, specifically: native S3 state locking, added in 1.10).
2. Declares every **provider** this project needs — a provider is a plugin that knows how to talk to a specific system's API. This project uses `aws` (obviously), `helm` and `kubernetes` (to install software *inside* the cluster Terraform itself just created — a deliberate blurring of "infrastructure" and "what runs on it," explained more below), `random` (to generate passwords), `null` (a generic escape hatch for running arbitrary scripts, explained below), `tls` (to fetch a certificate's fingerprint), and `kubectl` — specifically the *community* `gavinbunney/kubectl` provider, not HashiCorp's own `kubernetes` provider's manifest resource, because the community one can apply raw YAML at apply-time without needing to already know its exact structure ahead of time. That distinction matters because this project applies ArgoCD's own custom resources (`Application`, `ApplicationSet`) in the *same* apply that installs ArgoCD itself — HashiCorp's stricter provider would refuse, because it wants to validate the resource's shape against a schema that doesn't exist yet at plan time.
3. Configures the **backend** — where Terraform's own bookkeeping file (the "state file," which records what it believes currently exists) is stored. This uses an S3 bucket with `workspace_key_prefix` set, which is what makes `terraform workspace new staging` give you a completely separate, non-colliding state file automatically, without hand-editing any key names.

**Why does Terraform's state need to live in S3 at all, instead of just a file on your laptop?** Because more than one person (or CI) needs to run `terraform apply` against the same infrastructure, and if two people ran it with two different local state files, Terraform would have two different, conflicting beliefs about what exists — a recipe for creating duplicate resources or, worse, deleting something the other person's state file didn't know about. A shared S3 backend, combined with locking (so two applies can never run at the exact same instant), makes state a single, shared, safely-editable source of truth. This project uses S3's *native* locking (`use_lockfile = true`, an S3 conditional-write feature) rather than the older pattern of a separate DynamoDB table for locks — same guarantee, one less AWS resource to manage.

### `providers.tf` — configuring those plugins with real settings

Where `versions.tf` says "we need the `aws` provider," this file says "and here's what region, and here's how to authenticate." Three separate `aws` provider blocks exist: the default one (whatever `var.aws_region` is, normally `us-west-1`), one aliased `secondary` (for the DR region), and one aliased `us_east_1` (because AWS *requires* CloudFront's TLS certificate to live in `us-east-1` specifically, regardless of what region everything else is in — a fixed AWS rule, not a project choice). Every one of the three carries a `default_tags` block, meaning **every single resource Terraform creates automatically gets `Project`, `Environment`, `ManagedBy`, and `CostCenter` tags without each resource needing to repeat them** — a small detail, but it's what makes cost-reporting and "whose resource is this" queries possible later in the AWS Console or Cost Explorer.

The `helm`, `kubernetes`, and `kubectl` providers at the bottom are the interesting part: they authenticate to the *Kubernetes cluster this same Terraform run just created* (`module.eks.cluster_endpoint`), using a short-lived token fetched live via `aws eks get-token`. This is what lets one single `terraform apply` create the EKS cluster *and then*, in the same run, install Helm charts into it — you're not manually running `aws eks update-kubeconfig` and a separate `helm install` afterward.

### `data.tf` — the one-line file

Just `data "aws_caller_identity" "current" {}` — a **data source**, meaning "don't create anything, just look something up." This one looks up the AWS account ID and ARN of whoever is currently authenticated, and several other files reference it (to build IAM policy ARNs, or to grant "whoever's running this apply" cluster-admin automatically).

### `locals.tf` — named values computed once, reused everywhere

A "local" is a named expression, computed once, that other files can reference by name — the Terraform equivalent of a constant or a small helper computation. This file defines the VPC's address range (`170.20.0.0/16`), the exact list of public and private subnet CIDR blocks with their Availability Zones, and — worth calling out specifically — `eks_node_subnet_cidrs`, which slices *just* the first 4 private subnets out of the full list of 6. That sliced list exists for exactly one reason: the database's security group needs to allow traffic *only* from the subnets where EKS nodes actually live, not from the database's own subnets or anywhere else in the VPC — and this local is what makes that precise, rather than accidentally allowing the whole VPC's address range (which, worth knowing, is exactly what this project's database security group used to do, before a security review caught and narrowed it).

### `variables.tf` — every input this whole configuration accepts

Every `variable` block here is a knob someone running `terraform apply` can turn — a region, a domain name, whether DR replication is on, the alert email address, and so on. The important pattern to notice: almost every variable has a `validation` block attached — a rule that rejects an obviously-wrong value (a malformed email, a CIDR block that isn't real, a region string that doesn't look like a region) *before* Terraform ever tries to call AWS with it, turning what would otherwise be a confusing AWS API error 30 seconds into an apply into an instant, clear error at the very start. Two variables worth knowing by name because they show up in real incident stories: `enable_dr_replication` (explicitly default `false`, because it used to be silently controlled by a different, always-true condition — see the Architecture doc's DR section) and `alert_email` (deliberately has *no default* — you must supply it, because there's no sane default email address to guess).

### `outputs.tf` — everything this configuration hands back after it finishes

An `output` is a value Terraform prints after `apply` completes, and other tools (or humans) can read — things like the database endpoint, the ECR repository URLs, the Grafana dashboard URL, the CI role's ARN. A pattern worth noticing: several outputs are marked `sensitive = true` (the database secret ARNs, the JWT secret ARN, the SSH private key) — Terraform still computes and stores them, but won't print the actual value to your terminal by default, only a `(sensitive value)` placeholder, specifically so a screen-share or a CI log doesn't accidentally leak a credential.

### `main.tf` — the actual wiring: calling every module in order, and a few things that don't fit in a module

This is the file with the most going on, and it's worth reading top to bottom once, because it *is* the story of how the whole system comes together:

1. **`module "network"`** is called first, with no dependencies — everything else needs a network to live inside.
2. **`module "security_groups"`** — needs the VPC ID (from network) and the EKS-node subnet CIDRs (from `locals.tf`) to build the database's tightly-scoped firewall rule.
3. **`module "rds"`** — the database, wired to the security group and two specific private subnets. Notice `secondary_region = var.enable_dr_replication ? var.secondary_region : ""` — this is the exact fix for the "DR replication silently always on" bug: the region string is only passed through at all if the feature is genuinely opted into.
4. **Per-service database credentials, inline (not a module)** — instead of copy-pasting the same "generate a password, store it in Secrets Manager" pattern 4 times (once per service that owns data), this uses a single `for_each` loop over a small map (`catalog`, `user`, `order`, `notification`) with each service's schema/username baked in. This is a good, concrete example of the DRY principle (Don't Repeat Yourself) applied to infrastructure code — it used to be ~110 lines of near-duplicate resources, one block per service, and became roughly a fifth of that.
5. **The shared JWT secret, inline** — one random 64-character string, stored once, that `user-service` (to sign tokens) and every other service that needs to *verify* a token both read.
6. **`module "route53"`** — needs the database's endpoint (for the internal DNS record) and, notably, `primary_alb_dns = local.primary_alb_dns` — a value computed later, in `argocd.tf`, that auto-discovers the load balancer's hostname *within the same apply*, which is what eliminates what used to be a required second `terraform apply` (explained under `argocd.tf` below).
7. **`module "ecr"`** — same "off unless explicitly opted into" pattern for cross-region replication as RDS above, for the same underlying reason (a real incident where 6 unwanted ECR repos silently appeared in the DR region on every apply).
8. **`module "eks"`** — the Kubernetes cluster itself. Worth noting: `admin_principal_arns` always includes `data.aws_caller_identity.current.arn` — meaning whoever is running `terraform apply` right now *always* gets cluster-admin access automatically, every time, not just the first time the cluster was created. That's a deliberate fix for a real EKS quirk: EKS's own built-in "give the creator admin" behavior only fires once, at the literal moment of cluster creation, and does not retroactively apply to a different person running `apply` later.
9. **The SES/Alertmanager email block, inline** — this is the most unusual piece of code in the whole project, worth being able to explain in detail (see the dedicated section below).
10. **`module "monitoring_ec2"`** — the standalone monitoring server, with an explicit comment explaining *why* it does **not** have a blanket dependency on the entire `eks_addons` module (it only actually needs the Grafana password secret, which is one of the fastest things in that module — a blanket dependency would make it wait on ArgoCD's up-to-900-second install for no real reason).
11. **`module "eks_addons"`** last — everything that installs *inside* the cluster (external-secrets, the AWS Load Balancer Controller, ArgoCD, etc.), which obviously can't run before the cluster itself exists.

**The single most important thing to understand about `main.tf`'s structure:** Terraform does not execute top-to-bottom like a script. It builds a dependency graph from every resource reference (`module.network.vpc_id` used elsewhere means "whatever uses that must wait for network first") and runs everything it possibly can *in parallel*, only serializing where a real dependency exists. `rds` and `eks` don't depend on each other at all, so they build at the same time — this is why a full deployment takes roughly as long as whichever of those two is slower, not the sum of both.

### The SES/Alertmanager email block — worth its own explanation, because it's genuinely unusual

**The problem:** Alertmanager needs an SMTP username and password to send email through Amazon SES. But the actual SMTP password isn't the same thing as a normal AWS access key — AWS has a specific, published conversion algorithm (an HMAC-SHA256 chain, keyed with a fixed placeholder date) that turns an IAM secret access key into the SMTP password SES expects. **Terraform has no built-in function for HMAC-SHA256 chained this specific way.** Rather than hand-computing that value once and hardcoding it (which would leak it into the Terraform state file in plaintext, and never rotate), this project uses a `null_resource` with a `local-exec` provisioner — Terraform's escape hatch for "run an arbitrary local command as part of the apply" — to shell out to `python3`, compute the real password, and write it *directly* to Secrets Manager via the AWS CLI. **The derived password itself never becomes a Terraform value at all** — it exists only inside that one Python process's memory and Secrets Manager, never in state, never in a plan output.

**Why is this worth being able to explain well?** It's a genuinely good example of knowing *when to reach for an escape hatch* instead of forcing a tool to do something it fundamentally can't. Terraform is declarative — great at "ensure this resource exists with these properties," bad at "run this specific computation." Recognizing that boundary, and reaching for `local-exec` deliberately and narrowly (just for the one computation that needs it, writing the result straight to a secure store rather than back into Terraform's own bookkeeping) is exactly the kind of judgment call worth walking someone through if they ask "why does this file shell out to Python."

### `argocd.tf` — applying ArgoCD's own config, and solving the "chicken and egg" load balancer problem

Two separate things happen in this file:

1. It applies the three ArgoCD YAML files (`appproject.yaml`, `application.yaml`, `applicationset-microservices.yaml`) that live under `k8s/argocd/`, using `kubectl_manifest` — reading the *existing* files with `file()` rather than re-expressing their contents as Terraform/HCL. This is a deliberate choice: it means those YAML files remain the single source of truth (you can look at them directly, and ArgoCD itself reads the exact same files from git later), instead of having two different representations of the same configuration that could drift out of sync. `argocd_application` and `argocd_applicationset_microservices` both `depends_on` `kubectl_manifest.argocd_appproject`, because ArgoCD rejects either one naming a project that doesn't exist — real ordering, enforced by Terraform's dependency graph, not by a comment telling a human to apply things in the right order by hand.

   Worth knowing the history here: `appproject.yaml` genuinely was *not* wired into this file for a while — only `application.yaml` and `applicationset-microservices.yaml` were, and the AppProject itself was left as a manual, one-time `kubectl apply -f k8s/argocd/appproject.yaml` step documented in that file's own header comment. That's the kind of gap that's invisible on a long-lived cluster (the AppProject, once created by hand, just sits there — nothing ever asks "did Terraform create this?") and only became a real, visible outage the first time the whole cluster came up from a genuine `terraform destroy` + fresh `apply`, when every ArgoCD `Application` failed with `InvalidSpecError: Application referencing project bookstore which does not exist`. Fixed by adding the missing `kubectl_manifest` resource — same pattern as the other two files, just one that had been skipped.

2. It solves a genuinely tricky sequencing problem, and one that got *harder*, not easier, when ingress-nginx was replaced with the AWS Load Balancer Controller (see the Architecture doc's Elastic Load Balancing section). Route53 needs to create a DNS record pointing at the load balancer's hostname — but that hostname doesn't exist until *after* the load balancer is provisioned, which can lag well behind whatever Terraform resource seemed to "finish" first. With ingress-nginx, the load balancer came from a Service that a Terraform-managed `helm_release` created directly — a straightforward, if laggy, wait. With the AWS Load Balancer Controller, the ALB is provisioned by the controller reconciling an **Ingress object that Terraform doesn't create at all** — it's deployed by ArgoCD, asynchronously, after Terraform merely creates the ArgoCD `Application` that points at it. That's two layers of asynchrony stacked on top of each other now: wait for ArgoCD to sync the Ingress into existence, *then* wait for the controller to provision the ALB and populate its hostname. Skipping this entirely would mean running `terraform apply` once, manually checking the load balancer's hostname, pasting it into a variable, and applying *again* — a real, annoying two-step process this project has specifically engineered around, twice now, as the underlying infrastructure changed. The fix is a two-stage `null_resource`: poll for the Ingress object to exist first (a plain retry loop — `kubectl wait` needs its target to already exist, it doesn't wait for a resource's creation, only for a condition on one that's already there), *then* `kubectl wait --for=jsonpath=...` for the ALB's hostname specifically. The result — `local.primary_alb_dns`, now read via `data "kubernetes_ingress_v1"` instead of the old `data "kubernetes_service"` — feeds into `module.route53` back in `main.tf`, all within one single `apply`.

### `dr.tf` — the one real piece of cross-region disaster recovery

A single resource: `aws_db_instance_automated_backups_replication`, which tells RDS to continuously replicate the database's automated backups into the secondary region. It requires a real customer-managed KMS key that already exists *in that secondary region* (AWS's own managed encryption key is region-locked and can't be used for cross-region replication — a real AWS limitation, not a project choice), and it's entirely gated behind `var.dr_kms_key_id != ""`, meaning by default, with no key supplied, this resource simply doesn't exist. This is the honest, minimal, currently-real piece of DR in the whole project — see the Architecture doc for why it's important not to overstate what this means.

### `cloudfront.tf` — a real, working, currently-unused CDN

Both resources here (`aws_acm_certificate.cloudfront` and `aws_cloudfront_distribution.frontend`) use `count = var.enable_cloudfront && var.primary_alb_dns != "" ? 1 : 0` — meaning if the feature flag is off (the default), Terraform creates literally zero of these resources. It's fully-written, real code, sitting dormant until someone flips one variable. Worth knowing: the `default_cache_behavior` deliberately sets `min_ttl`/`default_ttl`/`max_ttl` all to `0` — meaning CloudFront does *not* cache dynamic content (like API calls) by default, only the specifically-configured `/static/*` path pattern gets real caching (a full year's max-TTL, appropriate for content that changes only when its filename does, like a hashed JS bundle).

### `ingress-cert.tf` — the ALB's real TLS certificate, and the discovery trick that avoids a chicken-and-egg problem

A second, *regional* ACM certificate — separate from `cloudfront.tf`'s, which is hard-pinned to `us-east-1` by an AWS requirement and physically can't be used by anything outside CloudFront. This one is where the ALB actually terminates HTTPS.

**The clever part, worth being able to explain:** nothing in this file's output — no ARN — ever gets written into any Kubernetes YAML file. That's deliberate, not an oversight. The AWS Load Balancer Controller supports **automatic certificate discovery**: give it an `Ingress` object with a `host` rule (or a `tls.hosts` entry) for `bookstore.example.com`, and if you *don't* set a `certificate-arn` annotation, the controller searches ACM for a certificate matching that hostname and attaches it itself. This sidesteps a real, structural timing problem: this certificate doesn't exist until a `terraform apply` creates it, but the `Ingress` YAML is plain, static content sitting in git, deployed independently by ArgoCD on its own schedule — there's no clean moment where "the freshly-created ARN" could get written into "the checked-in file" without adding a whole new manual or scripted bootstrapping step. Letting the controller find the certificate by matching hostnames, instead of being told the exact ARN, means Terraform and the Kubernetes manifests never need to talk to each other about this value at all.

Unlike `cloudfront.tf`'s certificate (which requests DNS validation but never actually finishes it in Terraform — harmless today only because CloudFront itself is off), this one completes the full validation loop for real: `aws_route53_record.ingress_cert_validation` writes the DNS records ACM asks for, and `aws_acm_certificate_validation` blocks until ACM confirms them and marks the certificate issued. That's a hard requirement here, not a nice-to-have — the controller's auto-discovery only matches *issued* certificates, never pending ones.

**A real gap worth knowing, caught by actually running this against two differently-shaped hostnames:** `subject_alternative_names` originally listed just `["*.${var.domain}"]`. A wildcard SAN only ever covers **one** additional label — `*.example.com` matches `bookstore.example.com` (one label deep) but never `api.bookstore.example.com` (two labels deep), by design, the same for any TLS certificate from any issuer. This project's two Ingress hosts sit at exactly those two different depths (`bookstore.<domain>` for the frontend, `api.bookstore.<domain>` for the gateway), so the single wildcard silently left the gateway's Ingress with no matching certificate — the AWS Load Balancer Controller logged `no certificate found for host: api.bookstore.<domain>` and simply never finished provisioning that one Ingress, while the frontend's, one label shallower, worked the whole time. Fixed by adding a second SAN, `*.bookstore.${var.domain}`. Because `subject_alternative_names` changing forces a full certificate replacement (a different set of SANs is a different ACM resource, not an in-place update), this needed `lifecycle { create_before_destroy = true }` to be safe — the replacement certificate gets created and validated before the original is torn down, so there's no window where the ALB has no valid certificate at all.

### `cloudtrail.tf` and `guardduty.tf` — the audit trail and the threat detector

`cloudtrail.tf` creates an encrypted, versioned S3 bucket, a bucket policy granting *only* the CloudTrail service permission to write to it (locked to CloudTrail's specific expected path prefix and requiring `bucket-owner-full-control`, so even a compromised CloudTrail configuration couldn't grant some other AWS account read access to your logs), and one multi-region trail. It also carries a lifecycle policy (added during the FinOps pass) that moves aging log objects to cheaper storage tiers over time, since audit logs need to be *retained*, not necessarily kept instantly-accessible forever.

`guardduty.tf` is a single resource enabling three specific, individually-toggleable data sources: S3 access-pattern analysis, Kubernetes audit-log analysis, and EBS malware scanning. Worth knowing for a cost conversation: all three carry real, non-zero per-GB or per-scan costs — this isn't a free checkbox, it's a deliberate security-vs-cost tradeoff, turned on because the security value was judged worth it.

### `iam.tf` — the GitHub OIDC trust relationship

Covered in depth in the Architecture doc's IAM section — the short version here: one IAM role, trusted only by GitHub's OIDC identity provider, only for tokens claiming to be from this exact repository, only on three named branches, with a narrowly-scoped policy that can push images to ECR repositories starting with `bookstore-` and nothing else. Worth noting the trust condition explicitly lists three branches (`main`, `improvements`, `observability`) — this list is a real, sharp edge: a fourth branch added later that also needs to push images would silently fail authentication until someone remembered to add it here too, which is exactly what happened once in this project's history (the `observability` branch itself was originally missing from this list).

### `observability-rbac.tf` — letting the monitoring server read from inside Kubernetes

The monitoring EC2's Prometheus needs to reach two things that live *inside* the Kubernetes API's permission model, not AWS's: raw kubelet metrics on each node (real per-pod CPU/memory usage) and each pod's own `/metrics` endpoint via the API server's proxy. Neither of those is covered by the generic "view everything" EKS access policy already granted to the monitoring server's IAM role — so this file creates a small, purpose-built Kubernetes `ClusterRole`/`ClusterRoleBinding` granting exactly the two permissions needed (`nodes/proxy` and friends, `pods/proxy`), bound to a *group name* rather than the specific IAM role's ARN directly. That group-not-ARN choice matters: if the monitoring EC2 is ever replaced (a new instance, a new IAM role session), binding to a stable group name means this permission grant doesn't have to be touched — only the *access entry* connecting the IAM role to that group name needs to exist, and that's managed separately, in `modules/monitoring-ec2`.

## Part 2: The modules — one folder, one job, each

### `modules/network`

Creates the VPC, all 8 subnets, the Internet Gateway, the single NAT Gateway (with its own Elastic IP), both route tables and their subnet associations, VPC Flow Logs (a record of every network connection in and out, for security investigation later, retained 90 days), and — added later — the free S3 Gateway VPC Endpoint that keeps ECR/S3 traffic off the paid NAT path. Also contains one genuinely subtle piece of defensive code: a `null_resource` that, *only during a real `terraform destroy`*, force-deletes the flow-log CloudWatch log group after a short pause. Why that's needed: AWS's VPC Flow Logs service will *recreate its own destination log group* if it notices the log group is gone but flow logs are still actively being delivered — a genuine "the service healed itself against you" scenario that was breaking clean destroys until this was added.

### `modules/security`

The smallest module — one security group (for RDS) and one rule: allow MySQL's port 3306, but only from the EKS-node subnet CIDR list computed in root `locals.tf`. No egress rule exists on purpose — a database that never needs to *initiate* an outbound connection doesn't need permission to.

**Inputs:** `vpc_id` (where the SG lives), `prefix` (naming), `eks_node_cidr_blocks` (the exact list that got narrowed from "whole VPC" to "just the node subnets" — its own `description` field in the code literally documents the bug it fixed, so the variable's own definition is self-explanatory to a future reader without needing to go find the incident writeup). **Outputs:** `rds_sg_id` — the one thing every other module that needs to attach this security group to something (the `rds` module itself) actually needs back.

### `modules/rds`

The database itself: MySQL 8.0, Multi-AZ, gp3 storage, storage-encrypted, automated backups with a 7-day retention window, Enhanced Monitoring (a more detailed, OS-level view of database performance than the default CloudWatch metrics give you), and three explicitly-declared, retention-bounded CloudWatch log groups for the database's error/general/slow-query logs (added later — without declaring these ahead of time, AWS creates them automatically with no expiry at all the moment the database starts writing to them, which quietly grows a storage bill forever). Also generates the admin password with the `random` provider and stores it in Secrets Manager — the actual value is never typed by a human, never appears in any file.

**Inputs, worth scanning once because every one of them enforces a real-world constraint via a `validation` block:** `db_allocated_storage` must be ≥20GB (RDS's own hard floor for MySQL), `backup_retention_period` must be 0–35 (RDS's own hard ceiling), `max_allocated_storage` must be 0 (disabled) or ≥20GB. Two variables are quietly important and easy to overlook: `kms_key_arn` (default `null` — meaning "use AWS's own managed key," which is exactly why cross-region backup replication in `dr.tf` needs a *different*, explicitly-supplied key, since AWS-managed keys can't leave their region) and `rotation_lambda_arn` (default `""`, meaning automatic credential rotation is off by default — a real Lambda function would need to be deployed separately and its ARN supplied here to turn it on; this project doesn't do that today). **Outputs:** `rds_instance_id`, `rds_instance_arn` (consumed by `dr.tf`'s backup-replication resource), `rds_subnet_group`, `db_credentials_secret_arn`, and `rds_endpoint` — which has one of the most consequential one-line comments in the whole codebase: it deliberately returns `aws_db_instance.db.address` (the bare hostname) and not `.endpoint` (host **and** port glued together with a colon). Every single consumer of this value — every service's `DB_HOST` environment variable, the private Route53 CNAME — expects a bare hostname it can hand to a DNS resolver or a database driver's `host` parameter, neither of which can parse an embedded `:3306` stuck on the end. Getting this wrong (which an earlier version of the code did) means *every database connection in the entire project silently fails* with a DNS resolution error, because `"host:3306"` isn't a valid hostname to look up at all — this single output's correctness is a precondition for literally everything else in the system working.

### `modules/route53`

Two hosted zones: a **private** one, only resolvable from inside the VPC, used for internal database DNS; and a **public** one, with active-passive failover records (backed by an HTTPS health check against the live site) pointing at the load balancer. This module is also where the "what LB type is this really" question bit hardest in practice — **three times**, worth understanding the whole arc, not just the current state, because it's a genuinely good example of a fact that kept changing out from under a piece of code that had to stay correct anyway:

1. The ingress load balancer started out genuinely being a **Classic ELB** (an accident, not a choice — ingress-nginx's default when nothing tells it otherwise). `data "aws_elb_hosted_zone_id" "ingress_lb" {}` — the classic-v1-only, no-argument data source — was the *correct* one to use at the time, even though the project's own docs kept incorrectly calling it an "NLB."
2. A fix was planned to switch to a real **NLB** (a Service annotation on ingress-nginx — the smallest change that would have made the "NLB" the docs already claimed actually true), which would have meant `data "aws_lb_hosted_zone_id" "ingress_lb" { load_balancer_type = "network" }` — the ELBv2 data source, NLB variant. This was coded but **never applied** — see step 3.
3. Before that NLB fix ever shipped, a follow-up question ("isn't ingress-nginx itself outdated?") surfaced that ingress-nginx had been officially retired by the Kubernetes project entirely — the NLB fix would have kept an unpatched, EOL, internet-facing component running, just with a slightly better load-balancer type in front of it. The real fix replaced ingress-nginx outright with the AWS Load Balancer Controller, which provisions an **ALB**, not an NLB — so this data source changed a *third* time, to `load_balancer_type = "application"`, without the NLB version ever having been live even once.

Getting this data source right requires knowing, precisely, which of the real load-balancer generations and types (classic v1 vs. v2, and within v2, ALB vs. NLB) the cluster is *actually* running at that exact moment — not what a doc claims, not what a previous fix planned, not what it used to be — which is why the module's own comment now spells out the full three-step history so the next person doesn't have to reconstruct it from git blame, and explicitly says to check `aws elbv2 describe-load-balancers` against the live account before ever touching this line again.

**Inputs:** `vpc_id`, `rds_endpoint` (feeds the private CNAME), `domain`, `primary_alb_dns`/`secondary_alb_dns` (both default `""` — empty on a brand-new cluster before the load balancer exists yet, which is exactly why `argocd.tf`'s auto-discovery mechanism matters), `enable_cloudfront`/`cloudfront_domain` (switch the public record's target between the load balancer directly and CloudFront). **Outputs:** `public_zone_id` and `public_name_servers` — the second one is the value a human has to manually copy into their domain registrar's NS records, the one manual step Terraform genuinely cannot automate away, since it requires action on a *different* system (the registrar) that Terraform has no API access to. Worth being precise about when this is needed: not just once, ever, but **every time this zone gets recreated** — a `terraform destroy` deletes the zone along with everything else, and the next `apply` generates brand-new, randomly-assigned NS values, since Route53 never reuses a domain's previous ones. Skip re-pointing the registrar after a from-scratch rebuild and ACM certificate validation (and anything depending on it, like the ALB's TLS listener) hangs indefinitely — public DNS resolvers simply can't reach the new zone's validation records until the registrar points at them. Caught for real the first time this project did a genuine destroy-and-rebuild of this exact migration: the ACM certificate sat in `PENDING_VALIDATION` for over an hour before anyone thought to check `dig NS <domain> @8.8.8.8` against what the live zone actually expected.

### `modules/ecr`

Creates one container image repository per service, all with `IMMUTABLE` tag mutability (a pushed tag can never be overwritten — once `v1.2.3` exists, it exists forever with that exact content, which is what makes a tag a trustworthy, auditable reference instead of a moving target), vulnerability scanning on every push, and a lifecycle policy that automatically expires anything past the most recent 10 images per repository, so old, unused image layers don't accumulate storage cost forever. Cross-region replication (for DR) is the same "off unless explicitly opted into" pattern seen elsewhere.

**Inputs:** `prefix`, `image_retention_count` (default 10), `secondary_region` (default `""`, off), `extra_repos` (the list of short service names — `catalog-service`, `user-service`, etc. — that get combined with the always-present `frontend` repo to build the full repository set). **Outputs:** `frontend_repo_url`, `registry_id`, and `repo_urls` — a generic map built with a `for` expression (`trimprefix(full_name, "${var.prefix}-") => repo.repository_url`) that strips the `bookstore-` prefix back off each repo name, so consumers can look things up by the short, human name (`repo_urls["catalog-service"]`) instead of needing to know the exact prefixed AWS resource name. This map pattern is exactly what let a 6th service be added later with zero changes to this module — one more entry in `extra_repos`, and it just appears in the map automatically.

### `modules/eks`

The Kubernetes cluster itself, and the most consequential module in the project. Key pieces:
- The **KMS key** used for Kubernetes Secrets envelope encryption (explained in the Architecture doc).
- The **cluster resource**, with all 5 control-plane log types enabled (API server, audit, authenticator, controller-manager, scheduler) and a dedicated, retention-bounded CloudWatch log group declared *before* the cluster, for the same "don't let AWS auto-create an unbounded log group" reason as RDS's logs above.
- **Access entries**, ensuring whoever runs `apply` always has cluster-admin, regardless of who originally created the cluster.
- The **OIDC provider**, which is the foundation everything using IRSA (External Secrets, the EBS CSI driver, etc.) depends on.
- The **node launch template**, which is where each worker node's boot-time script (`node-user-data.sh.tftpl`) is attached, installing `node-exporter` and `Fluent Bit` as systemd services directly on the node — a deliberate choice explained in the Architecture doc's monitoring section — plus an explicit gp3 root volume declaration (added later; previously left to an undeclared, implicit default).
- The **managed node group** itself, and its unusual `lifecycle.ignore_changes` pin — worth being able to explain precisely: this account's EC2 vCPU quota has *zero* spare headroom over what this project's node group + monitoring server already use, and a rolling replacement of the node group (which any launch-template change would normally trigger) needs one extra, temporary "surge" node during the swap. With no quota headroom for that surge node, a real rolling update attempt failed outright (`VcpuLimitExceeded`), and this `ignore_changes` line is what stops Terraform from repeatedly trying and failing the same rollout on every subsequent apply — it deliberately pins the node group to whatever launch template version is already live, until the quota is raised and someone deliberately removes the pin.

### `modules/eks-addons`

Everything installed *inside* the cluster via Helm or as a managed EKS "addon," split across several files by topic:
- `vpc-cni.tf` — turns on the VPC CNI's built-in NetworkPolicy enforcement (without which every NetworkPolicy YAML in `k8s/` is silently inert), plus the managed `metrics-server` addon, without which every HorizontalPodAutoscaler in the project would show `<unknown>` for its target metrics forever, unable to scale on anything.
- `ebs-csi.tf` — the driver that lets Kubernetes actually provision real AWS EBS volumes when something asks for persistent storage.
- `external-secrets.tf` — installs the External Secrets Operator and its IRSA trust policy, scoped specifically to `system:serviceaccount:external-secrets:external-secrets-sa` — meaning even if some *other* service account somehow requested this same IAM role, AWS's own trust-policy condition would refuse it; the binding is to one exact, named Kubernetes identity.
- `gitops.tf` — installs ArgoCD and Argo Rollouts. Worth noting the code comment explaining that these two Helm charts, and the others in this module, all install fully in parallel today — an earlier version of this project serialized several of these installs (waiting on each other one at a time) purely as a workaround for a much smaller, single-node cluster running out of resources during simultaneous installs; once the node group grew, that workaround was removed as unneeded overhead, not as a functional requirement anyone depended on.
- `grafana-secret.tf` — generates and stores the Grafana admin password, entirely independent of any of the slower Helm installs above (which is exactly why `module.monitoring_ec2` back in root `main.tf` can depend on just this, not the whole module).
- `aws-load-balancer-controller.tf` — installs the **AWS Load Balancer Controller**, same IRSA shape as `external-secrets.tf`. This is what actually provisions the ALB, by watching for Kubernetes `Ingress` objects and translating them into real ALB target groups/listeners/rules — genuinely replaces two files that used to exist here: `ingress.tf` (the old NGINX Ingress Controller install) and `cert-manager.tf` (Let's Encrypt certs for the ingress — no longer needed once TLS moved to an ACM certificate the controller auto-discovers by hostname; cert-manager had no other consumer in this project, so it was removed outright rather than left installed-and-idle). The IAM policy attached to this role is pasted in **verbatim** from AWS's own published `iam_policy.json`, not hand-written — 15 statements, easy to get subtly wrong by hand, and a good example of knowing when *not* to "clean up" or simplify something you're transcribing exactly. See the Architecture doc's Elastic Load Balancing section for the full why-not-ingress-nginx story.
- `observability.tf` — literally just a comment. It exists specifically to document, at the exact spot someone would expect to find a Prometheus Helm release, *why there isn't one* — a deliberate anti-confusion marker, not dead code.

### `modules/monitoring-ec2`

The standalone monitoring server: an Ubuntu EC2 instance, a security group scoped to `admin_cidr_blocks` for its UI ports (Grafana, Prometheus, Alertmanager) and to the VPC CIDR specifically for Loki's log-push port, an EKS access entry (bound to a stable group name, not the instance's own identity, for the replacement-safety reason explained under `observability-rbac.tf` above), and an auto-generated SSH key pair (fetched later via `make monitoring-key`) — added specifically because this instance originally had no way to SSH into it at all, neither a security-group rule for port 22 nor a key pair to authenticate with. The instance's entire configuration (Docker Compose, all four monitoring tools, dashboard JSON) is delivered via a single, gzip-compressed `user_data` script — compressed specifically because the plain-text version kept bumping against EC2's 16KB user-data size limit as more features were added over time.

**Inputs worth knowing individually, because each one answers a different "why does it need that" question:** `eks_cluster_sg_id` (lets this module add *inbound* rules onto the EKS cluster's own security group, from the monitoring server — three separate scrape paths: node-exporter on 9100, the EKS API on 443 for kube-state-metrics, kubelet's cAdvisor endpoint on 10250 for real per-pod CPU/memory); `eks_api_server` (the cluster's HTTPS endpoint URL, used by Prometheus's Kubernetes service-discovery config to find pods to scrape via the API server's proxy — deliberately templated from a live Terraform value rather than ever hardcoded, because a hardcoded literal IP address here is exactly what broke this before, the moment the cluster was ever recreated with a new endpoint); `grafana_admin_secret_arn`/`alertmanager_smtp_secret_arn` (exactly the two ARNs this instance's IAM role is allowed to read — nothing broader); `admin_cidr_blocks` (default wide-open `0.0.0.0/0`, with its own `description` explicitly telling the reader to narrow it in a real deployment). **Outputs:** four URLs (`grafana_url`, `prometheus_url`, `alertmanager_url`, `loki_url`), all built from the same `aws_eip_association.monitoring.public_ip` value with a different port appended, plus `instance_public_ip` and the `sensitive`-flagged `ssh_private_key_pem`.

## Part 3: How Terraform actually executes — the mechanics, precisely

Everything above explained *what* each file does and *why*. This part is for "no doubts" — the actual internal machinery, so a follow-up question about *how* something works has a real answer, not a hand-wave.

### The dependency graph — Terraform doesn't read your files top-to-bottom

The single most important mechanical fact about Terraform: **it does not execute in the order you wrote the file.** Before doing anything, Terraform parses every `.tf` file in the configuration and builds a **directed graph** — a map of "this resource's configuration references that resource's attribute, therefore this one must be created/updated after that one." A line like `db_security_group_id = module.security_groups.rds_sg_id` inside the `rds` module call *is* a graph edge — Terraform doesn't need you to declare "wait for security_groups," the reference itself is the dependency.

Once the graph exists, Terraform walks it and does **as much as it possibly can in parallel**, only serializing where a real edge forces it to. That's the precise mechanical reason `rds` and `eks` build simultaneously in this project (see `main.tf`'s walkthrough above) — nothing in either module's configuration references anything the other one produces, so there's no edge between them, so nothing forces them to wait on each other.

**`depends_on` is the explicit escape hatch** for the rare case where a real dependency exists but *isn't* expressed through a value reference — for example, `module.monitoring_ec2`'s `depends_on = [null_resource.ses_smtp_password]`: the monitoring module reads the SMTP *secret's ARN* (a value that exists the instant the empty secret shell is created), but it actually needs the secret's *contents* to be populated by that separate local-exec script first, and nothing about "I read this ARN" naturally captures "and also wait for that unrelated script to finish." `depends_on` states that ordering requirement directly, since no attribute reference could express it on its own.

### The state file — what's actually in the notebook, and why hand-editing it is dangerous

The state file (stored in S3 here, per `versions.tf`) is a JSON document mapping every resource address (`module.eks.aws_eks_cluster.this`, for instance) to the *last known real-world values* Terraform saw for it — not just "this exists," but every attribute AWS reported back at the time. Every `plan` starts by **refreshing** state (re-reading real values from AWS for everything it manages) before comparing against your configuration — meaning Terraform's picture of reality is only ever as fresh as the last `plan`/`apply`, and if someone changes something by hand in the AWS Console in between, Terraform will detect that drift on the next `plan` and, unless told otherwise, plan to revert it back to match the configuration. This is the exact same "reconcile reality to match the declared source of truth" idea as ArgoCD's `selfHeal`, one layer further down the stack, and worth naming as such if the parallel comes up.

**Why the state file is dangerous to hand-edit, and why this project never does:** the state file is the *only* record Terraform has linking a configuration resource address to a real AWS resource ID. Corrupt or mismatch that link, and the next `apply` might try to create a duplicate of something that already exists, or — worse — believe something exists that was actually deleted out from under it and error out confusingly. The only sanctioned way to fix a state/reality mismatch is Terraform's own `import`/`state` subcommands, never opening the JSON in an editor.

### `for_each` versus `count` — why the per-service secrets use one, not the other

Both are ways to create multiple copies of the same resource block from one piece of code. **`count`** takes a number and creates resources addressed by *index* (`resource[0]`, `resource[1]`, ...). **`for_each`** takes a map or a set and creates resources addressed by *key* (`resource["catalog"]`, `resource["user"]`, ...). The per-service database credentials in root `main.tf` deliberately use `for_each` over `local.db_service_credentials` (a map keyed by service name), not `count` over a list — and the reason is a real, sharp footgun `count` has: if you use `count` over a list and later remove an item from the *middle* of that list, every item *after* it silently shifts down one index, and Terraform reads that as "destroy the old index N, create a new index N" for every single shifted item — even though, semantically, nothing about most of those items actually changed. `for_each`'s key-based addressing means removing `"order"` from the map only ever affects the one resource keyed `"order"` — everything else (`"catalog"`, `"user"`, `"notification"`) is completely untouched, because their addresses were never index-based in the first place.

### Sensitive values — what `sensitive = true` actually does, and doesn't do

Marking an output or variable `sensitive = true` tells Terraform's CLI to print `(sensitive value)` instead of the real value in `plan`/`apply` output and in `terraform output` by default — a screen-share safety net. **It is not encryption, and it does not remove the real value from the state file** — the actual plaintext is still stored in the state JSON (which is exactly why the state file itself needs to live somewhere access-controlled and encrypted, like this project's S3 backend with `encrypt = true`, and why nobody should ever casually paste state file contents anywhere). Marking something sensitive is a UI/display safeguard against accidental exposure in logs and terminals, not a security boundary on its own.

### How the providers actually authenticate — the exact mechanics, not just "it authenticates"

Two genuinely different authentication flows are worth being able to describe precisely, because "it just logs in" isn't a real answer:

**AWS provider (whoever is running `terraform apply`):** typically your own AWS CLI credentials, resolved the normal AWS SDK way (environment variables, a shared credentials file, or an assumed role) — nothing project-specific here, this is standard AWS tooling behavior.

**The `helm`/`kubernetes`/`kubectl` providers, authenticating to the cluster this same run just created:** this is the interesting one. Each of those provider blocks in `providers.tf` has an `exec` block that runs `aws eks get-token --cluster-name ... --region ...` *live, every time Terraform needs to talk to the cluster* — not a stored credential, a freshly-generated one on each invocation. That command uses your already-authenticated AWS identity to generate a short-lived Kubernetes-compatible bearer token, valid for about 15 minutes, via AWS's `sts:GetCallerIdentity` mechanism combined with EKS's own token-verification logic on the API server side. Nothing about your Kubernetes access is a separate, second credential to manage — it's derived, on the spot, from the exact same AWS identity already being used for everything else in the apply.

**The GitHub Actions CI role — the other authentication flow worth knowing precisely, since it's genuinely different from both of the above:** GitHub's own OIDC token service issues a signed JWT (JSON Web Token) unique to that specific workflow run, containing claims like "this is repo X, branch Y, workflow Z." That JWT is presented to AWS's Security Token Service via the `sts:AssumeRoleWithWebIdentity` API call. AWS independently verifies the JWT's signature against GitHub's published public keys (via the OIDC provider registered once, out-of-band, in `iam.tf`'s prerequisite comment) and checks the JWT's claims against the IAM role's trust policy conditions (`token.actions.githubusercontent.com:sub` must match one of the three allowed branch patterns). Only if all of that matches does STS hand back temporary AWS credentials, valid for the rest of that one job. No password, no long-lived key, ever exchanged at any point in this flow — the trust is rooted entirely in GitHub's signature and AWS's independent verification of it.

## Questions you should be ready for

**"Why 8 separate modules instead of one big Terraform configuration?"**
Same reasoning as microservices, one level down the stack: each module is independently understandable, independently testable in isolation, and changes to one (say, adding a new EKS addon) don't require re-reading or risking unrelated code (say, the RDS module). It's the infrastructure-as-code version of separation of concerns.

**"What happens if `terraform apply` fails halfway through?"**
Terraform's state file reflects exactly what it *actually* managed to create before the failure — it's not all-or-nothing like a database transaction. Re-running `apply` picks up from there: anything already created is left alone (assuming it still matches the desired config), and Terraform only attempts the parts that didn't finish. This is why idempotency (the property that applying the same config twice produces the same result, with no duplicate side effects) is such a core design goal throughout — several of this project's own scripts (schema-init SQL, for instance) are deliberately written to be safely re-runnable for exactly this reason.

**"Explain `terraform plan` vs `terraform apply` like I've never used either."**
`plan` is a dry run — it tells you exactly what *would* change, with nothing actually touched yet, the same way `git diff` shows you changes without committing them. `apply` is where those changes actually happen against real infrastructure. Never running `apply` without having read the `plan` output first is the single most important operational habit in this whole workflow.

**"What's a provider, one more time, simply?"**
A plugin that knows how to talk to one specific system's API and translate Terraform's generic "create/read/update/delete" language into that system's real requests. The `aws` provider speaks AWS's API; the `helm` provider speaks Helm's; without the right provider, Terraform has no idea how to act on a given kind of resource at all.
