# Future Improvements

What's next, in three buckets: finish what's in flight, fix known gaps, then the longer-term roadmap. Written from the actual current state of `observability` (last reviewed 2026-08-14) — not aspirational, and not a copy of the old `FUTURE.md` (which described a pre-EC2-monitoring, pre-microservices state that no longer matches this codebase).

## In flight: the microservices platform

All 5 plans are implemented and committed:

1. **`catalog-service`** — done ([Plan 1](superpowers/plans/2026-07-30-catalog-service.md)).
2. **`user-service`** — done ([Plan 2](superpowers/plans/2026-08-01-user-service.md)) — auth/JWT, register/login, own `user_db` schema.
3. **`order-service` + `notification-service`** — done ([Plan 3](superpowers/plans/2026-08-01-order-notification-service.md)) — place order/list orders, plus a best-effort (not queued) call to notification-service on order placement.
4. **`api-gateway`** — done ([Plan 4](superpowers/plans/2026-08-01-api-gateway.md)) — Node/Express + `http-proxy-middleware`, centralized JWT verification, path-routes to all four backend services, real public `Ingress` for `api.bookstore.<domain>`.

5. **The frontend** — done ([Plan 5](superpowers/plans/2026-08-08-frontend-microservices-integration.md)) — login/register, cart, checkout, order history, all wired to `api-gateway` via a shared authenticated API client. `Books`/`Add`/`Update` were switched from the old backend's URL to the gateway too, and gated behind login the same way the new pages are, since the gateway now requires a JWT for any write.

**Full backend retirement — done.** Plan 4's own final task (deleting `backend/` and its K8s manifests once api-gateway proved out) was paused for a full session rather than run blind, then executed explicitly once confirmed dead: zero ingress routes, zero references anywhere in the live frontend bundle. `backend/`, `k8s/base/backend/`, every backend-only manifest (configmap, PDB, NetworkPolicy, schema-init Job, canary AnalysisTemplate, `hpa-backend.yaml`), the 6 backend CI steps, and the `bookstore-backend` ECR repo (all image history, `force_delete=true`) are all gone. See [`TROUBLESHOOTING.md`](TROUBLESHOOTING.md) OBS-046.

**Observability extension — done.** The EC2 Prometheus's scrape config now covers real per-pod resource usage (kubelet cAdvisor, `nodes/proxy` RBAC — see OBS-044) and every microservice's own `prom-client` `/metrics` (via the API server's pod-proxy, annotation-gated — see OBS-045). Pod/traffic alert rules, a cluster overview dashboard (OBS-048), and real email alert notifications via SES SMTP (OBS-053, `config.env`'s `ALERT_EMAIL`) are all live. Log shipping (Fluent Bit → Loki) is implemented but not yet rolled out — see OBS-050/OBS-051. No per-service/cross-service Grafana dashboards beyond the two auto-imported community ones (Node Exporter Full, Kubernetes cluster monitoring) yet — that part's still open if it turns out to matter.

Explicitly **not** in scope for this platform, by deliberate design-spec decision (see the spec's Non-goals): service mesh/mTLS, async messaging (SQS), per-service RDS instances, distributed tracing. These are real gaps, not oversights — see "Longer term" below for where they'd fit if this platform keeps growing.

## Known gaps that should get fixed properly

These aren't "nice to haves" — they're specific, already-identified problems with a clear fix, listed roughly in the order they'd bite you.

1. ~~**CI's OIDC trust policy doesn't cover the `observability` branch.**~~ **Fixed** — see [`TROUBLESHOOTING.md`](TROUBLESHOOTING.md) OBS-005. Requires a `terraform apply` to actually take effect if you're reading this before that's run.

2. **`ApplicationSet`'s `targetRevision: observability` is tracked only by a code comment.** Once the microservices branch merges to `main`, nothing forces `k8s/argocd/applicationset-microservices.yaml` to switch back — and every future service added to the `elements` list inherits whatever `targetRevision` is already there. Worth either a tracked issue, or a cheap CI check that fails if any `k8s/argocd/*.yaml` on `main` references a non-`main` `targetRevision`.

3. **`eks_bootstrap.py`, at the repo root, is very likely dead code.** It predates `modules/eks-addons` — back when cert-manager/ESO/ingress-nginx/ArgoCD were installed by hand via a Python script instead of Terraform `helm_release` resources. Confirm nothing still calls it (check any remaining references in scripts, Makefile, CI, or docs), then delete it. Leaving unused infrastructure-provisioning scripts around invites someone running the wrong one during an incident.

4. **`scripts/bootstrap-tf-state.sh` duplicates `scripts/init-backend.sh`.** The former prints a backend block for manual paste-in; the latter patches `versions.tf` automatically and is what `DEPLOYMENT.md` actually tells people to run. Keep one, probably `init-backend.sh` (it's strictly more automated), and either delete the other or clearly mark it superseded.

5. ~~**`k8s/base/database/` (MySQL StatefulSet/Service/ConfigMap) is dead code sitting on disk.**~~ **Fixed** (2026-08-14) — confirmed unreferenced by any `kustomization.yaml`, then deleted. See [`TROUBLESHOOTING.md`](TROUBLESHOOTING.md) OBS-054.

6. **`k8s/base/monitoring/servicemonitor.yaml` and `prometheus-rules.yaml` are inert CRDs.** Nothing installs the Prometheus Operator that would consume them (Prometheus runs on EC2, scrapes via static/file_sd configs — see [`ARCHITECTURE.md`](ARCHITECTURE.md)). Either actually wire them up (would mean installing the Operator, a real architecture change already rejected once for resource reasons — see TROUBLESHOOTING TF-006) or delete them so they stop implying a capability that doesn't exist.

7. **No graceful shutdown in any Node service.** None of `services/catalog-service/`, the other microservices, or future services handle `SIGTERM` — a pod termination during a rolling update can drop in-flight requests instead of draining them. Small, mechanical fix, same pattern in every service: `process.on('SIGTERM', () => server.close(() => process.exit(0)))`.

8. **`ACM`'s redundant `ignore_changes` warning** ([`TROUBLESHOOTING.md`](TROUBLESHOOTING.md) TF-004) — harmless but permanent noise on every plan/apply. One-line fix, just hasn't been prioritized.

9. **Single NAT gateway, no per-AZ redundancy.** A deliberate cost tradeoff today (see [`TERRAFORM.md`](TERRAFORM.md#module-network)) but a real single point of failure for all private-subnet egress. Still true — an S3 Gateway Endpoint was added (2026-08-14, OBS-054) to cut the *volume* of traffic that has to transit it (ECR pulls, S3 API calls), which reduces the NAT's data-processing cost and blast radius somewhat, but doesn't touch the availability gap. Worth revisiting once this stops being purely a demo/reference deployment.

10. ~~**The ingress load balancer is a Classic ELB, not an NLB — despite every doc in this project (this session's own docs included) calling it "NLB."**~~ **Superseded, then fixed for real** (2026-08-15, OBS-056 → OBS-057). A same-day follow-up question ("isn't ingress-nginx itself outdated?") caught this gap's original planned fix — an NLB annotation on ingress-nginx — before it was ever applied, and surfaced the actual, bigger issue: **ingress-nginx was officially retired by the Kubernetes project on 2026-03-31**, no more CVE patches ever, for a controller directly on the public internet. Fixed by replacing ingress-nginx entirely with the AWS Load Balancer Controller (AWS's own official migration recommendation), provisioning a real ALB via Ingress objects instead of an NLB via a Service annotation. See OBS-057 for the full migration (new ACM cert, cert-manager also removed since it had no other consumer, a real NetworkPolicy bug caught by actually building the Kustomize output, the Route53/argocd.tf discovery mechanism rewritten for Ingress-based rather than Service-based discovery). The predicted brief downtime from the LB getting recreated is still real and still pending explicit apply approval — not casually skipped.

11. ~~**ingress-nginx metrics are never actually scraped, so `backend`'s canary analysis (`error-rate` AnalysisTemplate) is a no-op that always passes.**~~ **Moot** — the `backend` Rollout and its `AnalysisTemplate` were deleted along with the rest of the old monolith (see OBS-046). Ingress-nginx's `/metrics` still isn't scraped, but nothing depends on it for a canary gate anymore, since there's no canary deploy anywhere in the platform right now. Worth revisiting only if a canary strategy gets added to one of the microservices.

12. ~~**`k8s/base/ingress/ingress.yaml` and `k8s/services/api-gateway/base/ingress.yaml` both claim the host `api.bookstore.<domain>`.**~~ **Fixed** as part of [Plan 5](superpowers/plans/2026-08-08-frontend-microservices-integration.md) — `k8s/base/ingress/ingress.yaml`'s `api.bookstore.<domain>` rule (both the `rules` entry and the `tls.hosts` entry) was removed, leaving `k8s/services/api-gateway/base/ingress.yaml` as the sole owner. Verified live via ArgoCD sync + a real curl against the gateway: `POST /books` without a JWT now returns `401` from `api-gateway`, confirming the old backend isn't answering that host anymore.

13. **`terraform destroy` doesn't clean up everything it created.** Confirmed via a real AWS-account audit after a full destroy cycle on 2026-08-05: EKS/EC2/RDS/NAT/ELB/EIPs/Secrets Manager/CloudFront/VPC endpoints all torn down cleanly, but (a) EBS volumes created dynamically by the EBS CSI driver for K8s `PersistentVolumeClaim`s are never in Terraform state, so they're orphaned as `available` (unattached) volumes after the cluster is gone — cost keeps accruing until deleted by hand; (b) ECR repos (`ecr` module) don't have `force_delete` set, so `terraform destroy` on a repo with images in it fails or leaves the repo+images behind depending on how it's invoked; (c) K8s-created security groups (e.g. `k8s-elb-...`, created by the in-tree cloud provider for LoadBalancer Services) aren't in Terraform state either and can block the VPC itself from being deleted if destroy runs before the LoadBalancer Service is cleaned up. None of these are large dollar amounts individually, but on a project that gets destroyed/recreated often during development (see TROUBLESHOOTING TF-015/TF-017), they add up silently. Worth a documented post-destroy checklist, or a `make destroy-verify` target that runs the same audit queries.

14. ~~**`k8s/base/monitoring/analysis-template.yaml` hardcodes the monitoring EC2's Elastic IP as a literal, so every full destroy/recreate silently breaks canary rollouts.**~~ **Moot** — the file itself was deleted along with the `backend` Rollout it gated (see OBS-046). The underlying "don't hardcode a value that changes every destroy/recreate" lesson is still worth remembering if a canary strategy gets added to a microservice later — use the real `prometheus_url` Terraform output via a ConfigMap, not a checked-in literal.

15. ~~**A `terraform apply` touching `module.eks`/`module.eks_addons` has now deleted the live ingress-nginx `LoadBalancer` Service and caused real downtime twice**~~ **Moot as of OBS-057** — ingress-nginx, and the specific `null_resource.delete_ingress_nginx_lb` resource whose unexplained destroy-time firing caused both incidents, are both gone, replaced by the AWS Load Balancer Controller and its own `null_resource.delete_ingress_objects`. Whether the *new* resource has the same "fires outside a real destroy" failure mode is genuinely unknown — it hasn't been through a real destroy/recreate cycle yet — so treat this as "the specific historical bug is gone," not "the underlying risk class is proven fixed." Kept below as the historical record of what happened twice with the old mechanism, in case the new one ever needs debugging the same way:

    The original two incidents: first via an unrelated node-count change (OBS-031), then again during the OBS-051 node-group apply's failure/retry cycle (OBS-052). `modules/eks-addons/ingress.tf`'s `null_resource.delete_ingress_nginx_lb` had a `when = destroy` provisioner meant only for genuine `terraform destroy`-time cleanup (it deliberately avoided leaving an orphaned Classic ELB behind, since `helm_release`'s own destroy doesn't reliably clean that up), but it kept firing outside that path — twice, from two different triggers, neither one a real `terraform destroy`. Root cause was never fully pinned down beyond "something about a failed/retried or resize apply near this resource causes it to be destroyed and recreated." Both times, recovery was manual: extract the Service manifest from `helm get manifest ingress-nginx -n ingress-nginx` and `kubectl apply` it back, then re-`terraform apply` so Route53 picked up the new hostname.

16. **This AWS account's default EC2 vCPU quota (8, `L-1216C47A`) has zero headroom over this project's steady-state footprint** (3× `t3.medium` node group + 1× `t3.small` monitoring EC2 = 8 vCPU exactly). Any future EKS managed-node-group launch-template change needs surge capacity for its rolling replacement and will hit `NodeCreationFailure`/`VcpuLimitExceeded` the same way OBS-051 did — request a quota increase (`aws service-quotas request-service-quota-increase --service-code ec2 --quota-code L-1216C47A --desired-value 16 --region <region>`) proactively, rather than discovering this mid-apply again. `aws_eks_node_group.this` currently carries a `lifecycle.ignore_changes` guard (see OBS-051) specifically to stop this from being retried automatically — remove it once the quota clears.

17. **Workspace-based state isolation exists (`versions.tf`'s `workspace_key_prefix`, see [`TERRAFORM.md`](TERRAFORM.md#environments)) but resource *naming* isolation doesn't.** Almost every AWS resource name in this project is a hardcoded `"bookstore-*"` literal, not derived from `terraform.workspace`/`var.environment` — two workspaces applied against the same AWS account would collide on real resource names (`aws_eks_cluster` named `bookstore-eks` can only exist once per account+region) even though their Terraform state is correctly separate. Safe today only because this project has only ever run one environment at a time. Fixing this for real means threading `var.environment` (or `terraform.workspace`) into every hardcoded name across all 8 modules + root — a real, moderately large refactor, not a config tweak, and worth its own plan rather than doing it opportunistically.

18. **FinOps audit done (2026-08-14, OBS-054) — everything that didn't need the EC2 vCPU ceiling raised is fixed.** RDS gp2→gp3, S3 Gateway Endpoint, bounded CloudWatch log retention (EKS control plane + RDS exports), CloudTrail bucket lifecycle policy, `CostCenter` tag, explicit gp3 node root volume, ingress-nginx HA + PDB fix (same single-replica anti-pattern OBS-049 fixed for the backend services, missed here since it's a Helm value not a `k8s/` file). Deliberately **not** done, and why: (a) **Cluster Autoscaler / Karpenter** — would fix the fact that all 6 HPAs are correctly configured but capped by the fixed 3-node group's spare capacity, but its whole point is adding node capacity on demand, which needs vCPU headroom this account's quota (8, see OBS-051) doesn't have; (b) **Spot instances** — same total vCPU as On-Demand, but Spot is tracked against a separate, unconfirmed quota, and adds interruption risk to a node group already in OBS-051's fragile pinned state; (c) **Reserved Instances / Savings Plans** on RDS + the monitoring EC2 (both steady-state, long-running, good candidates, biggest $ lever identified) — a real Billing-console financial commitment, not something to automate. Revisit (a) and (b) together once the vCPU quota increase clears — Karpenter bounded to the same ceiling would still improve bin-packing over the current static allocation, just not by adding capacity.

## Test coverage

- `catalog-service`'s tests verify HTTP response shape but (as of the original implementation) didn't assert on what was actually passed to the DB query mock — a params-order regression (e.g. swapping `price`/`desc`) could have shipped silently. Fixed for catalog-service during code review (added `toHaveBeenCalledWith` assertions on POST/PUT), but **apply the same pattern to every future service's tests from the start**, not as a retrofit.
- No integration tests anywhere — every test suite uses a mocked DB query function. Fine for unit-level CRUD logic, but nothing currently exercises a real MySQL connection, real schema constraints, or real ExternalSecret-sourced credentials end-to-end.
- `client/` (the React frontend) has real unit test coverage as of Plan 5: `AuthContext`'s state transitions (login/register/logout, localStorage persistence, both success and failure paths), the shared `api.js` client's auth-header and 401-redirect interceptors, and the cart/orders-to-books join helper — 18 tests total. What's still untested is every page component itself (`Login`, `Register`, `Cart`, `Checkout`, `Orders`, `Books`, `Add`, `Update`) — verified by hand against the live cluster instead, a deliberate scope decision (see the Plan 5 design spec's non-goals), not an oversight. No frontend E2E test infra exists.

## Frontend design system (client/src/style.scss)

A source-code-only design review (no live cluster to screenshot against — infra was destroyed at the time) found `style.scss` is 124 lines, the app's *only* stylesheet (`App.css` is dead CRA boilerplate, imported nowhere), with zero CSS variables, zero `@media` queries, and zero `:focus` rules. Ten concrete bugs from that review are already fixed (missing alt text, invalid `button`-wrapping-`Link` nesting, a dead duplicated CSS declaration, no keyboard-focus styling, under-44px touch targets, silent-to-screen-readers cart feedback, an off-pattern error render on two pages, no disabled-while-submitting state on four forms, no responsive breakpoints at all, and a missing empty-state on the catalog page — see the `style(design): FINDING-0xx` commits on this branch for each).

**Deliberately left unfixed, and why — these are design-system decisions, not bugs, and don't belong in an unprompted refactor:**
- **No color token system.** Colors are a mix of CSS keywords (`teal`, `white`, `gray`) and raw `rgb()` triples with no shared palette or semantic naming — e.g. `.delete`'s red and `.error`'s red are the same value by coincidence, not by reference to a shared token. Worth a real `$variables`/CSS-custom-properties pass, but that's an architecture choice (SCSS vars vs. CSS custom properties vs. a design-tokens file) the project should make deliberately, not have picked implicitly by whichever fix happened to touch a color first.
- **No typography scale.** Zero `font-size` declarations anywhere — every heading/paragraph/button's size is accidental browser-default UA styling, not a designed hierarchy. Same reasoning: introducing a scale is a real design decision (what ratio, what base size), not a one-line fix.
- **No spacing scale.** 8 distinct magic-number spacing values (`10px`, `15px`, `20px`, `30px`, `50px`, `100px`, plus a couple of oddballs), no shared base unit. Low risk to fix mechanically, but doing it well means picking a real scale (4px or 8px base) and touching every value at once — a dedicated pass, not folded into an unrelated finding's commit.

## Longer term

Once the 5-service platform is stable and the deferred items above are actually needed (not preemptively):

- **Service mesh (Istio).** mTLS between services, fine-grained `AuthorizationPolicy`, traffic-shifting canaries per service instead of just the gateway. Big enough to warrant its own design spec when it's time — don't bolt it on incrementally.
- **Async messaging (SQS/SNS).** Replace order-service's synchronous best-effort call to notification-service with a real queue. The current sync approach was chosen deliberately to defer this cost, not because it's the intended end state.
- **Per-service RDS isolation.** Today every service shares one RDS instance with per-service schemas/users. Real isolation (separate instances, or at minimum separate parameter groups / separate backup policies) is the natural next step once schema-level isolation stops being enough.
- **Distributed tracing (X-Ray or Jaeger via Istio).** Only useful once there are actually multiple services in a single request path worth tracing — premature before the gateway + at least 2-3 backend services are live.
- **Multi-region active-active**, not just backup replication. Would need a second EKS cluster in `us-west-2` and a real strategy for keeping RDS in sync (cross-region read replica promotion, most likely) — currently `dr.tf` only replicates backups, there's no compute to fail over to.
- **Cost optimization, remaining pieces** — see gap #18: Karpenter + Spot for the node group are both deferred on the EC2 vCPU quota, not forgotten. RDS storage-autoscaling tuning and right-sizing everything based on real CloudWatch data once there's real traffic to measure are still open regardless of the quota.
- **Gateway API**, now that OBS-057 has the AWS Load Balancer Controller installed anyway. AWS's own migration guidance frames `Ingress` + `alb.ingress.kubernetes.io/*` annotations (what OBS-057 actually did) as the *immediate* replacement for ingress-nginx, and Gateway API (`GatewayClass`/`Gateway`/`HTTPRoute` — a different object model, CNCF-GA since October 2025, `AWS Load Balancer Controller v3.0+` supports it) as the *future* direction, deliberately not bundled into the same change — adopting a whole new API model under the time pressure of an EOL security fix would have been exactly the kind of unforced scope creep this project tries to avoid. Worth a real design spec when it's time, using `ingress2gateway` (Kubernetes SIG-Network's own migration tool, 1.0 as of March 2026) rather than hand-converting.
- **Database migration tooling** (Flyway/Liquibase) instead of ad-hoc SQL in bootstrap Jobs — worth it once there are enough services/schemas that hand-written bootstrap SQL stops scaling.

## Architecture decisions worth remembering (so they don't get silently re-litigated)

- **EKS over EC2/ASG** — the original project had both paths; EC2/ASG (launch templates, ASGs, bastion) was fully removed. EKS is the only path now.
- **RDS over in-cluster MySQL** — dev/demo convenience of in-cluster MySQL was rejected in favor of RDS everywhere, specifically to avoid a "works on my cluster, breaks in prod" gap. The dead `k8s/base/database/` files are the leftover of that decision (see gap #5 above).
- **External Secrets Operator over Sealed Secrets** — already committed to AWS, Secrets Manager gives rotation/versioning/IAM-scoped access without meaningfully more complexity than Sealed Secrets would.
- **GitHub OIDC over static AWS keys** — no long-lived credentials in GitHub Secrets anywhere in this pipeline. A misconfigured trust policy fails loudly at auth time; a leaked static key fails silently and much worse.
- **Monitoring on EC2, not in-cluster** — not a preference, a resource-constraint decision (see TROUBLESHOOTING TF-006). Revisit only if the node group grows meaningfully past its current size, and even then, weigh the operational simplicity of "monitoring lives outside the thing it's monitoring" before moving back in-cluster.
- **Microservices split is platform-first, not feature-first** — the design spec deliberately scoped this as "5 real services + observability" and explicitly deferred mesh/async/tracing/full-isolation rather than trying to build the complete distributed-systems stack in one pass. Don't accidentally scope-creep a future plan into rebuilding what was deliberately deferred.
- **The old backend/monolith cutover was deliberately left as a separate, manual decision, not automated away — and that paid off.** Deleting `backend/`/`k8s/base/backend/` was paused rather than run as part of the same session that built api-gateway. It was genuinely still-referenced at that point (serving the old frontend). By the time it was actually deleted, a full session of further verification had confirmed zero references anywhere — irreversible deletion of a once-production path got its own explicit go-ahead at the right moment, not a plan auto-completing through it prematurely. See OBS-046.
